# 生活关系与事件图设计

## 1. 设计目标

本模块不把用户定义为单一的“丈夫”“父亲”或“子女”等身份，而是将人物、事件、资金目标和待执行动作组织成一张属于当前用户的生活关系图。

同一个用户可以同时存在多条关系，例如：

```text
本人 --SPOUSE_OF--> 爱人 --HAS_EVENT--> 爱人生日
本人 --PARENT_OF--> 女儿 --HAS_EVENT--> 学费缴纳日
生日礼物心愿金 --TRIGGERED_BY--> 爱人生日
女儿学费目标   --TRIGGERED_BY--> 学费缴纳日
```

这样，Agent 理解的是“用户与哪些人、哪些事件和哪些目标有关”，而不是给用户贴一个不可变化的身份标签。

## 2. 为什么 LangGraph 不保存关系图数据

LangGraph 是 Agent 工作流编排工具，不是图数据库。当前实现使用 MySQL 保存业务事实，并使用 LangGraph 编排“识别事件、补充信息、检测冲突、请求确认、恢复和人工接管”，原因如下：

- 关系规模较小，MySQL 足以支持查询、事务、审计和用户隔离。
- 银行业务需要明确的数据约束，不能只依赖模型输出或运行时状态。
- LangGraph 检查点只保存最小流程进度，不能覆盖 MySQL 中的候选请求和正式图谱事实。

LangGraph 只通过服务层读取经过授权的数据并提交候选变更，不直接绕过 Repository 写数据库。正式实现见 [`LANGGRAPH_WORKFLOW.md`](./LANGGRAPH_WORKFLOW.md)。

## 3. 核心数据模型

### 3.1 图节点 `life_graph_nodes`

统一表示图中的实体，首期支持三类节点：

| 节点类型 | 说明 | 示例 |
| --- | --- | --- |
| `PERSON` | 当前用户及其声明的关系人 | 本人、爱人、女儿 |
| `EVENT` | 有时间含义的生活事件 | 生日、学费缴纳日 |
| `GOAL` | 需要资金规划的目标 | 礼物心愿金、学费目标 |

每个节点都包含 `owner_user_id`，任何读取和修改都必须使用 JWT 中的当前用户作为归属条件。

### 3.2 关系边 `life_graph_edges`

关系边表达节点之间的语义，例如：

- `SPOUSE_OF`：配偶关系。
- `PARENT_OF`：亲子关系。
- `HAS_EVENT`：某个人关联某个事件。
- `TRIGGERED_BY`：目标由某个事件触发。

边同时保存：

- `provenance`：信息来源，首期仅允许 `USER_DECLARED` 写入正式图谱。
- `confidence_bp`：置信度，使用 0 到 10000 的整数表示，避免浮点误差。
- `consent_scope`：用户授权的用途，例如只允许提醒或目标规划。
- `valid_from` / `valid_until`：关系有效期，避免把历史关系永久当作当前事实。

数据库通过复合外键保证边的起点和终点都属于同一个用户，防止跨用户串图。

### 3.3 生活事件 `life_events`

保存事件的业务属性，包括事件类型、发生时间、时区和重复规则。时间在数据库中按既有时间规范保存，展示和自然语言理解使用 `Asia/Shanghai`。

生日可使用 `FREQ=YEARLY`，一次性学费缴纳日则不设置重复规则。

### 3.4 资金目标 `financial_goals`

保存目标金额、已预留金额、截止时间、币种和资金策略。金额使用定点数，不使用浮点数。

首期的 `funding_policy` 只描述候选策略，例如“确认后预留”。创建目标不等于执行资金划转，真实扣款仍必须进入现有黄/红色权限链路。

### 3.5 待执行动作 `scheduled_actions`

保存提醒、预留建议等定时动作，并通过用户级 `idempotency_key` 防止重复执行。动作至少关联一个事件或目标。主动雷达的租约、重试、审计和飞书投递说明见 [`LIFE_EVENT_RADAR.md`](./LIFE_EVENT_RADAR.md)。

### 3.6 候选变更 `life_graph_change_requests`

保存尚未进入正式生活图谱的候选节点、关系、事件、目标和动作。每条请求包含用户级幂等键、结构版本、内容快照哈希、过期时间和决策状态。

`PENDING` 表示仅供用户核对；只有确认服务在同一数据库事务中完成正式图谱写入后，状态才会变为 `APPROVED`。拒绝、过期或取消的请求不会修改正式图谱。

## 4. 写入与安全边界

LLM 不得直接写入生活图。完整写入链路为：

```text
用户表达
  -> LLM 提取候选人物、关系、事件和目标
  -> JSON Schema 校验
  -> 服务层检查用户归属、授权范围和重复项
  -> 向用户展示候选变更
  -> 用户确认
  -> Repository 在事务中写入
  -> 记录审计日志
```

必须遵守以下规则：

- 模型推断出的亲属关系不能自动成为正式事实。
- 涉及第三人的敏感信息只保存完成场景所需的最少字段。
- 用户可以查看、修改、停用和删除自己声明的关系与事件。
- Agent 只能在 `consent_scope` 允许的范围内使用关系数据。
- 资金目标冲突时只给出可解释的方案，不代替用户判断家庭成员的优先级。

## 5. 核心演示场景

用户说：“我爱人 11 月 18 日生日，帮我留 1000 元买礼物，提前两天提醒我。”

系统应创建爱人节点、配偶关系、生日事件、礼物资金目标和提醒动作。随后用户补充：“女儿 11 月 15 日要交 5000 元学费。”

如果预计可用资金无法同时覆盖两个目标，Agent 应：

1. 展示冲突的金额、日期和计算依据。
2. 提供调整礼物预算、延后非必要支出或更换资金来源等方案。
3. 等待用户选择，不擅自认定“配偶”或“子女”谁更重要。
4. 对任何真实资金操作继续执行黄/红色权限确认与审计。

该场景的获奖辨识度在于：系统不是普通的标签画像或消费推荐，而是在用户授权下理解生活关系、预见资金目标冲突，并保持银行级安全边界。

## 6. 分阶段实现与验收

### 阶段一：模型与迁移

- 建立节点、边、事件、目标和动作五张表。
- 验证同一用户多重关系可共存。
- 验证数据库拒绝跨用户图边。

### 阶段二：Repository 与 API

- 建立可持久化、可防篡改的候选变更请求。
- Repository 使用短事务直接访问数据库，所有查询都强制包含当前用户归属条件，不进入现有的内存状态整体重写流程。
- 同一用户使用相同幂等键和相同内容重试时返回原请求；内容不同则拒绝，避免请求重放改变原始授权对象。
- 提供图谱查询、候选变更确认、事件和目标增删改查。

首期用户级接口如下，全部要求 JWT，且不接受客户端传入用户 ID：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/life-graph` | 查询当前用户的正式生活图谱 |
| `PATCH` | `/api/life-graph/nodes/{node_id}` | 纠正人物名称、事件日期或目标金额，必须携带 `Idempotency-Key` |
| `GET` | `/api/life-graph/change-requests` | 查询当前用户的候选变更，可用 `status` 过滤 |
| `POST` | `/api/life-graph/change-requests` | 创建候选变更，必须携带 `Idempotency-Key` 请求头 |
| `GET` | `/api/life-graph/change-requests/{request_id}` | 查询单条候选变更 |
| `POST` | `/api/life-graph/change-requests/{request_id}/decide` | 确认或拒绝候选变更 |
| `GET` | `/api/life-graph/goal-conflicts` | 分析当前正式资金目标 |
| `GET` | `/api/life-graph/change-requests/{request_id}/goal-conflicts` | 将待确认目标与正式目标合并分析 |

创建接口首次成功返回 `201`；相同幂等键和相同内容重试返回原记录及 `200`；同一幂等键对应不同内容返回 `409`。
- 所有接口从 JWT 获取用户，不接受客户端指定 `owner_user_id`。
- 重复请求通过幂等键只执行一次。

### 阶段三：Agent 结构化意图

- DeepSeek 输出候选图变更 JSON，不输出 SQL。
- 支持“我爱人生日”“女儿学费”等多轮补槽。
- 低置信度或缺少关键日期、金额时必须追问。

当前实现新增 `life.event_plan` 意图，结构化槽位包括：

- `related_person` 与 `relation_type`：关系对象与关系类型。
- `event_type`、`event_date` 与 `recurrence_rule`：事件类型、具体日期和重复规则。
- `goal_required`、`target_amount` 与 `currency`：是否需要资金目标、目标金额和币种。
- `reminder_days_before`：提前提醒天数。

DeepSeek 通过严格 JSON Schema 输出；模型超时、不可用或输出不合法时，会回退到可离线复现的中文规则解析器。两条路径都必须遵守相同的缺失槽位规则。

示例对话：

```text
用户：我爱人下个月生日，帮我留 1000 元买礼物，提前两天提醒。
Agent：还需要补充具体日期。在补充完成前，不会执行任何资金操作。
用户：18 号。
Agent：已生成生活关系、生日事件、1000 元资金目标和提前两天提醒的候选方案，请核对后确认。
```

第二轮完成后，Agent Runtime 调用候选变更服务并进入 `WAITING_CONFIRMATION`。此时正式图谱仍为空；只有用户通过候选变更确认接口批准后，节点、关系、事件、目标和提醒动作才会在同一事务中写入。

### 阶段四：目标冲突检测

- 计算指定时间窗口内的可用资金与目标缺口。
- 输出计算依据和多个候选方案。
- 用户确认后才调整目标或进入资金操作。

当前实现使用以下可审计口径：

```text
可支配余额 = 活期可用余额 - 用户指定的保护金额
目标剩余金额 = 目标金额 - 已预留金额
余额缺口 = max(截至当月的累计目标剩余金额 - 可支配余额, 0)
现金流压力 = max(当月目标剩余金额 - max(近 30 天收入 - 近 30 天支出, 0), 0)
```

分析状态：

| 状态 | 含义 |
| --- | --- |
| `CONFLICT` | 累计目标超过可支配余额，存在明确资金缺口 |
| `PRESSURE` | 当前余额能够覆盖，但同月目标超过已观察净现金流，可能挤压日常支出 |
| `CLEAR` | 按当前证据暂未发现缺口或现金流压力 |
| `UNKNOWN` | 余额、币种或其他关键证据不足，不能判断 |

`protected_balance` 默认是 `0`，只能由用户或后续画像策略明确提供，系统不会偷偷设置保护金额。近 30 天现金流只作为可解释的压力信号，不会被当作未来必然收入。

核心演示中，爱人生日目标为 1000 元、女儿学费候选目标为 5000 元。如果近 30 天净现金流为 5000 元，系统会显示同月目标共 6000 元、现金流压力缺口 1000 元，并同时提供调整金额或日期、补充资金来源、经确认使用存量余额等选项。所有选项均为 `auto_apply=false`，最终选择始终属于用户。

### 阶段五：前端与演示

- 提供时间线和关系视图，允许用户纠正数据。
- 明确区分“系统建议”“等待确认”“已安排”和“已执行”。
- 演示生日目标与学费目标发生冲突的完整闭环。

当前前端已提供“对话 / 生活图谱”双视图。生活图谱工作区由以下部分组成：

- 关系视图：以账户本人为起点展示配偶、子女、父母等多重关系，同时展示用户授权用途。
- 事件时间线：按日期展示事件、关联人物、资金目标、目标状态和提醒时间。
- 候选确认：`PENDING` 方案以独立状态带展示；确认或拒绝后重新读取正式图谱和冲突证据。
- 冲突证据：展示保护金额、可支配余额、近 30 天净现金流、逐月缺口和不自动排序的安全声明。
- 资料纠正：人物可修改显示名称，事件可修改日期，目标可修改金额；所有纠正都要求填写原因。

桌面端采用关系、时间线和证据三栏协作布局；移动端改为单列，并保留候选确认、纠正和证据功能。浏览器验收覆盖 1440px 桌面视口和 390px 移动视口，移动端不存在页面级横向溢出。

#### 资料纠正实现

资料纠正是用户显式操作，不经过 LLM 推断，处理链路如下：

```text
用户填写纠正内容与原因
  -> 前端生成一次性 Idempotency-Key
  -> Pydantic 严格校验字段和金额范围
  -> 服务层校验 JWT 用户归属、节点类型和节点状态
  -> 在单个数据库事务中修改节点及关联业务记录
  -> 写入 source=USER_CORRECTION 的已批准快照
  -> 返回最新正式图谱
```

事件日期变化时，带 `days_before` 的待执行提醒会同步重排；目标金额不得低于已预留金额。同一幂等键和同一内容重试返回原纠正结果，同一幂等键对应不同内容时返回冲突，事务失败时原数据保持不变。

#### 错误契约与前端回退

业务异常统一使用下列响应结构，客户端不依赖 Python 异常文本，也不会接收到堆栈、SQL 或密钥信息：

```json
{
  "detail": {
    "code": "TARGET_AMOUNT_BELOW_RESERVED",
    "message": "目标金额不能低于已经预留的金额。",
    "retryable": false,
    "details": {}
  }
}
```

关键错误判断如下：

| HTTP 状态 | 错误码示例 | 处理原则 |
| --- | --- | --- |
| `401` | `NOT_AUTHENTICATED`、`INVALID_ACCESS_TOKEN` | 清理内存 Access Token，尝试一次安全续期或返回登录页 |
| `403` | `RESOURCE_FORBIDDEN` | 拒绝跨用户访问，不泄露资源内容 |
| `404` | `LIFE_GRAPH_NODE_NOT_FOUND`、`CHANGE_REQUEST_NOT_FOUND` | 将不存在和无权访问合并，降低资源枚举风险 |
| `409` | `CHANGE_REQUEST_REPLAYED`、`CHANGE_REQUEST_TAMPERED`、`CORRECTION_IDEMPOTENCY_CONFLICT` | 停止写入并保留原始数据，提示刷新或重新生成 |
| `409` | `TARGET_AMOUNT_BELOW_RESERVED` | 回滚事务，要求金额不低于已预留金额 |
| `422` | `INVALID_REQUEST` | 返回字段级校验信息，不进入服务层写入 |
| `503` | `LIFE_GRAPH_NOT_CONFIGURED` | 标记 `retryable=true`，提示稍后重试 |

前端请求默认 15 秒超时，超时转换为 `REQUEST_TIMEOUT`；只在服务端明确标记 `retryable=true` 时提示稍后重试。候选冲突分析若发现候选已确认或不存在，会回退分析正式目标，而不会让整个生活图谱空白。

### 阶段六：LangGraph 编排

- 编排提取、补槽、冲突检测、确认和执行节点。
- 支持中断、恢复、回退和人工接管。
- LangGraph 状态只保存流程进度，业务事实仍以 MySQL 为准。

当前已使用 LangGraph `1.2` 实现以下确定性状态图：

```text
                    +-> await_input --------------------------+
MESSAGE -> validate_slots                                     |
                    +-> create_candidate -> analyze_conflicts |
                                              -> await_confirmation

DECISION -------------------------------------> apply_decision
RECOVER  -------------------------------------> recover
HANDOFF --------------------------------------> human_handoff
ABORT   --------------------------------------> abort
```

节点职责如下：

| 节点 | 职责 | 是否允许直接修改正式图谱 |
| --- | --- | --- |
| `validate_slots` | 复核关系、事件、日期和目标金额是否完整 | 否 |
| `await_input` | 挂起流程并保存缺失槽位 | 否 |
| `create_candidate` | 通过 `LifeGraphService` 创建幂等候选请求 | 否 |
| `analyze_conflicts` | 读取候选与正式目标，输出可解释资金证据 | 否 |
| `await_confirmation` | 将控制权交还用户 | 否 |
| `apply_decision` | 接收事务服务已经完成的确认结果并推进 Run | 否 |
| `recover` | 后端重启后复核候选请求状态，恢复等待点或终态 | 否 |
| `human_handoff` | 冻结自动流程并进入人工队列状态 | 否 |

#### 检查点与恢复

没有另建 SQLite 或内存事实库。每次图推进后，只在现有 `agent_runs.payload.workflow` 中保存最小检查点：

- `stage`：当前流程阶段。
- `checkpoint_seq`：检查点序号。
- `trace`：实际经过的节点名称。
- `missing_slots`：仍需用户补充的字段。
- `change_request_id`：候选请求引用，不复制候选内容。
- `conflict_status`：最近一次冲突结论。
- `recovered`：是否经历后端重启恢复。

后端启动时只恢复 `WAITING_INPUT`、`WAITING_CONFIRMATION` 和 `WAITING_HUMAN` 流程。恢复确认流程时必须重新读取 MySQL 中的候选请求：仍为 `PENDING` 才继续等待；已批准或拒绝则同步到终态；请求缺失时停止自动推进并进入 `WAITING_HUMAN`。因此，LangGraph 检查点不能覆盖或伪造银行业务事实。

#### 人工接管与回退

`POST /api/agent/runs/{run_id}/handoff` 会执行以下操作：

1. 校验 JWT 用户是否拥有该 Run。
2. 冻结自动流程，撤销未完成的黄色确认或红色验证码。
3. 若存在生活图谱候选请求，以 `HUMAN_HANDOFF` 原因拒绝候选，防止接管后仍被并行确认。
4. 将 Run 置为 `WAITING_HUMAN`，保存原因和时间，并记录 `HUMAN_HANDOFF` 审计事件。

主动中断同样会拒绝尚未确认的生活图谱候选。之后再次确认将触发 `CHANGE_REQUEST_REPLAYED`，不会写入正式图谱。人工工作台及处理结果回传将在 Channel Gateway 阶段接入；当前阶段已经完成安全冻结和可审计排队状态。

## 7. 后续关系圈与资金优先级协商

人物关系图提供生活上下文，不提供资金支配权。后续家庭资金目标协商器将继续使用 MySQL 保存关系、事件、目标和用户明确声明的约束，并由 LangGraph 编排以下流程：

```text
读取关系圈与资金目标
  -> 追问刚性/弹性、截止日和最低保障金额
  -> 确定性计算余额与现金流冲突
  -> 生成多个可解释方案
  -> 等待用户选择
  -> 生成候选变更
  -> 用户再次确认后写入正式图谱
```

系统不得因为目标关联“配偶、父母、子女”等身份自行提高或降低优先级。优先约束只能来自用户明确输入或经过确认的目标属性；LangGraph 负责流程，不负责替用户做价值判断。每个方案必须展示计算证据、受影响目标和可撤销结果。
